# Bulk answer-generation review — 13 September 2026

## Executive conclusion

The run is operationally reliable but is not yet clinically reliable. All 100 questions completed and returned schema-valid answers, but manual comparison with the benchmark reference answers found only **18 passes (18%)**, **27 partial answers (27%)**, and **55 failures (55%)**. Only **4 of 50 topics (8%)** passed in both question phrasings, while **21 topics (42%)** failed in both phrasings.

The largest problem is not API availability or output formatting. It is weak evidence selection followed by generation that answers confidently from irrelevant, conflicting, or misread evidence. This is especially dangerous for thresholds, doses, contraindications, referral rules, and treatment timing. The system should not be used for clinical decision support in its current form.

## Scope and method

This review covers the live `Q_S1` run in [`20260913T124928720084Z`](../../artifacts/05_2_bulk_answer_generation/20260913T124928720084Z/). The run used `google/gemma-3-4b-it` through DeepInfra with prompt `evidence-answer/v2`.

Each generated answer in [`results.csv`](../../artifacts/05_2_bulk_answer_generation/20260913T124928720084Z/results.csv) was compared manually with its supplied benchmark reference answer:

- **Pass:** contains the essential answer and no material contradiction.
- **Partial:** contains useful correct content but misses a required qualifier, threshold, action, or other important part.
- **Fail:** off-topic, gives a wrong clinical fact or number, reverses the required action, merely repeats the question, or fails to answer the requested point.

This is a benchmark-grounded engineering review, not an independent clinical validation of the source guidelines.

## What mostly failed

### 1. Off-topic evidence dominates the answer

At least 28 answers contain obvious repeated contamination patterns:

- 14 answers repeat antenatal booking, antenatal-card, or “Mama buk” material: IDs 8, 12, 16, 20, 26, 38, 42, 52, 54, 58, 70, 72, 90, and 98.
- 14 answers repeat newborn resuscitation, bag-mask ventilation, cardiac massage, or `A.B.C.D` material: IDs 5, 11, 13, 15, 25, 41, 45, 53, 57, 67, 69, 83, 89, and 97.

Examples include the fever-and-feeding referral question answered with bottle-feeding instructions (ID 7), the child-weighing question answered with neonatal airway management (ID 11), the cotrimoxazole-prevention question answered with newborn resuscitation (ID 83), and the antenatal blood-pressure question answered with neonatal asphyxia management (ID 97).

This pattern explains much of the 55% failure rate and indicates systematic retrieval/context pollution rather than isolated model mistakes.

### 3. Contraindications and negative rules are poorly retrieved

Both CPAP contraindication answers failed to state that pneumothorax is a contraindication (IDs 29–30). Both answers to “CPAP requires breathing” described equipment instead of stating that CPAP is ineffective without spontaneous breathing (IDs 31–32). The rule not to give a single antibiotic dose also failed in both forms (IDs 15–16).

Negative rules such as “do not,” “will not,” and contraindications need dedicated handling because dropping the negation can turn an answer into unsafe guidance.

### 4. Tables are present but are not grounded by row and column

This is visible in two important examples:

- ID 49 received the F-75 table in `S1`, including the 5 kg daily total, but generated `50 ml`, apparently selecting an unrelated row/cell rather than resolving the 5.0 kg row and 3-hour column.
- IDs 75–76 received the DTG table and its exact “10 mg scored dispersible tablet,” “older than 4 weeks,” and “at least 3 kg” text. The answer nevertheless converted table quantities into incorrect strengths such as 1 mg, 3 mg, and 4 mg.

Plain Markdown table text inside a long context is not sufficient for dependable dose lookup with this model.

### 5. The system answers when it should abstain

All 100 records have status `answered`; none returned `insufficient_evidence`. This includes plainly unrelated outputs and answers whose needed fact was absent from the packed context. For example, ID 43's context contained older 13.5/14 cm MUAC criteria rather than the benchmark's 11.5 cm criterion, and ID 51 did not contain the required “second week” instruction. These cases should have been rejected as insufficient or conflicting evidence.

### 6. Correct evidence is sometimes present but ignored

Not all failures are retrieval failures. In sampled records, the correct facts were present in context but the generator failed to use them:

- ID 75 included the complete DTG eligibility statement and table.
- ID 81 included the exact high-risk and low-risk infant-prophylaxis schedules.
- ID 97 included `140/90` and pre-eclampsia evidence.
- ID 99 included “any bleeding after 20 weeks” and the admission rule, although the digital-examination restriction was absent.

This separates two defect classes that should be measured independently: **retrieval recall** and **answer faithfulness given retrieved evidence**.

## Likely technical causes

### Query construction is preserving benchmark boilerplate

The enhanced retriever removes a small filler list, but leaves terms such as `during`, `busy`, `clinic`, `face`, `situation`, `frontline`, `health`, `worker`, `asks`, `correct`, `action`, and `guideline`. Those terms are common in antenatal and general-care passages. They can outweigh the short discriminating topic phrase.

The phrase/proximity branches are only enabled when the focused query contains at most eight terms. The benchmark wrappers often keep the query above that limit, disabling the branches that could favor exact clinical phrases.

### Broad OR retrieval and reciprocal-rank fusion admit weak matches

Search defaults to OR mode, retrieves as many as 40 candidates per branch, fuses multiple branches, and returns five chunks. A chunk can therefore rank through multiple weak single-term matches. There is no minimum matched-term count, semantic relevance threshold, clinical-domain constraint, or source/version policy.

### Context expansion adds volume without a relevance gate

The five hits expand into as many as ten evidence groups. The average request contains about 12.6k evidence characters and 5k prompt tokens. Neighbor chunks are included based on adjacency, not on whether they answer the question. The small generator must then distinguish a short target fact from several unrelated passages.

### Validation is structural, not semantic

The implementation verifies evidence identity, JSON shape, and citation-label membership. It does not verify that an answer's claims, numbers, units, negations, population, or timing are supported by the cited passages. The artifact correctly records this limitation as `support_validation: not_performed`.

### Source conflicts and recency are unresolved

The MUAC and F-75 examples show multiple manuals or protocols with different cut-offs/schedules in the same corpus. The system has no explicit policy for jurisdiction, document type, publication date, supersession, or conflict abstention, so a retrieved but non-target protocol can drive the answer.

## Recommended improvements

### P0 — Add safety gates before another clinical-quality claim

1. **Implement claim-level support validation.** Split the answer into atomic claims and require each claim to be entailed by at least one cited passage. Check numbers, units, comparison operators, ages, durations, populations, and negations exactly. Reject or regenerate unsupported output.
2. **Fail closed on missing or conflicting evidence.** If no passage directly supports the requested fact, return `insufficient_evidence`. If sources disagree, report the conflict and identify source/version instead of selecting one silently.
3. **Add deterministic numeric validation.** Extract numeric facts from both answer and cited evidence and compare normalized values and units. Treat substitutions such as 11.5→13.5, 80→50, or 10 mg→1 mg as hard failures.
4. **Treat contraindications and negative instructions as protected facts.** Require preservation of `not`, `do not`, `avoid`, `contraindicated`, `only`, `before`, `after`, and threshold operators.
5. **Remove unsupported side advice.** Require a short direct answer to the asked topic. Any additional clinical instruction must have its own citation and pass entailment validation.

### P1 — Improve retrieval precision before changing the model

1. **Canonicalize the question.** Strip the two benchmark wrappers and search the clinical topic, or use the existing `topic` field directly during evaluation. Add the wrapper words listed above to query-noise handling.
2. **Use phrase-first candidate generation.** Always search the canonical topic as a phrase/proximity query. Use OR only as fallback, with a minimum number or proportion of matched discriminating terms.
3. **Add a reranker and rejection threshold.** Rerank candidates against the canonical question and discard low-relevance chunks rather than always returning five hits.
4. **Route by clinical domain/document metadata.** A lightweight classifier can constrain candidates to oxygen, CPAP, HIV, TB, nutrition, obstetrics, and so on. Keep cross-domain retrieval as an explicit fallback.
5. **Reduce context.** Start with the best two or three independently relevant chunks. Add a neighbor only when it supplies a continuation, table header, qualifier, or referenced section needed by a selected chunk.
6. **Model source precedence.** Store publication date, jurisdiction, guideline type, and supersession relationships. Prefer the applicable current source and force abstention when applicability cannot be resolved.

### P1 — Make tables first-class evidence

Parse clinical tables into structured records with explicit row and column labels, for example:

```json
{
  "protocol": "F-75 reference card",
  "weight_kg": 5.0,
  "frequency_hours": 3,
  "volume_per_feed_ml": 80,
  "daily_total_ml": 650
}
```

Retrieve the matching row deterministically, attach its source passage/page, and let the model verbalize the verified fields. Apply the same approach to ART weight bands, transfusion thresholds, drug doses, and oxygen thresholds.

### P2 — Improve generation after evidence quality is controlled

1. Test a stronger instruction-following model against the same frozen retrieval outputs. The current 4B model misreads tables and ignores relevant facts even at temperature zero.
2. Ask for structured atomic claims rather than a free-form answer/reason pair. Each claim should carry its citation and typed values such as `value`, `unit`, `operator`, `population`, and `condition` where applicable.
3. Put the question and highest-confidence evidence first, clearly separate relevant evidence from optional supporting context, and explicitly prohibit answering adjacent topics.
4. Use a second-pass verifier or deterministic rules to decide accept, regenerate with reduced context, or abstain. Do not let the answer model self-certify support without an independent check.

## Evaluation plan for the next iteration

Measure the pipeline in stages so retrieval and generation failures cannot hide each other:

1. **Retrieval recall:** does top-k contain the exact benchmark-supporting passage?
2. **Retrieval precision:** what proportion of packed evidence groups directly concerns the clinical topic?
3. **Oracle generation:** generate from the known supporting passage only. This establishes whether the model can answer when retrieval is perfect.
4. **End-to-end answer quality:** repeat this manual rubric and add exact numeric/negation checks.
5. **Citation entailment:** percentage of atomic claims supported by their cited passages, not merely valid label references.
6. **Paraphrase robustness:** require the two phrasings of each topic to produce equivalent clinical facts.

Recommended release gates for this benchmark:

- zero wrong numeric thresholds, doses, timings, contraindications, or referral rules;
- 100% claim-support validation coverage;
- at least 80% full-pass answers and no more than 5% failures;
- at least 75% of topics passing in both phrasings;
- every non-answerable or conflicting case returning `insufficient_evidence` rather than a guessed answer.

Run controlled ablations in this order: canonical query → phrase/minimum-match retrieval → relevance reranking → smaller context → structured tables → stronger generator → independent support verifier. Preserve the same question set and artifact format so each change can be compared directly with this baseline.

## Final assessment

The pipeline mechanics, artifact completeness, latency, and schema enforcement are solid enough to support iterative experiments. The current answer-quality bottleneck is chiefly **retrieval precision and evidence packaging**, with a second major issue in **generation faithfulness and table interpretation**. Citation-label validity should not be presented as groundedness until claim-level support validation is implemented.
